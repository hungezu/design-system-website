# 设计 Markdown 的 AI 可用性检查

日期：2026-09-19。

## 结论

旧产出不足以可靠指导 AI：快照规则太笼统，历史规则与当前 API 不同，API 摘要还遗漏了真实交互回调。已修复生成链。新规范可以作为项目实现约束，但使用方仍必须提供匹配组件包与业务需求，不能把 Markdown 当作可执行组件库。

## 已修复的问题

| 优先级 | 问题 | 处理 |
|---|---|---|
| P1 | 新 ai-rules.md 只有一段原则，缺少读取顺序和缺失处理 | 新快照生成明确的读取与消费规则 |
| P1 | API 生成器过滤 onClick、分页和排序等业务回调 | 保留项目声明的事件；MD 包含全部必填属性和业务回调 |
| P1 | 无项目专属 DESIGN.md，容易把平台黑色或本地演示包带进业务页面 | 按冻结项目/版本生成规范，项目包内加入 DESIGN.md，网站增加独立下载 |
| P1 | 根 DESIGN.md 把 danger 混为 variant；旧快照要求所有输入使用 DSSelect | 根文档更正稳定 API；新规则区分 DSInput / DSTextArea / DSSelect，旧不可变发布保留 |
| P2 | 字体描述 Token 容易被误当作合法 font 简写 | 说明描述值与 CSS 可用变量的区别，示例使用实际预览字体/字号变量 |
| P2 | patterns.json 条目容易被当成 React 导出 | 明确其为元数据；禁止假定项目包导出 TemplateExample 等演示组件 |

## 证据

- 新规范带 schema、scope、项目短 ID、发布 ID、版本、运行时、快照校验值和包名。
- 生成器只读取冻结快照，不读取当前草稿、App UI Token 或其他项目。
- 规范中提供批准组件清单、冻结 Token、必要 API、布局/交互/状态规则、代码示例和验收标准。
- 两个项目、三个测试版本安装真实 tarball 到工程目录外的独立 npm 工程；从包内 DESIGN.md 原样提取示例，全部通过 TypeScript 检查。
- 故意把值回调改为 event.target.value，类型检查确实失败；不是只检查语法或文本存在。
- Token 引用全部存在，安装包/下载文档内容一致，项目、版本和主题数据互相对应。
- 独立 Vite 页面成功运行：默认 12 条数据分两页，切到每页 20 条后回到第一页并显示全部 12 条；筛选“验收资源 12”后只保留 1 条。按钮实际颜色为测试版本的 #6236FF，浏览器错误日志为空。
- 隔离工作区的版本页实际显示组件包、接入说明与 AI 设计规范三个下载入口。没有在用户工作区发布测试版本。
- 相关单元测试 15 项、服务端交付/权限等 31 项通过；完整主站回归和构建通过。保持已有 chunk 体积提示。

机器可读结果：`artifacts/design-md-acceptance/verification.json`。
样例文件：`artifacts/design-md-acceptance/<project>/<version>/DESIGN.md`。8.x 版本为验收夹具，不是用户发布。

## 边界

没有调用外部 AI 模型，也没有做跨模型生成成功率评测。当前证据覆盖文档契约、真实包的类型/构建和浏览器消费行为；不能据此保证任意模型一次生成正确。历史发布包不重写，缺少匹配代码归档的版本仍不可冒充可执行交付。
