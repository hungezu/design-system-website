# 项目组件如何交付给前端

更新：2026-09-19。本文保留原方案；项目版本打包、网页生成下载和独立业务参考工程现已实现。当前用法、验证与剩余范围以 [实现记录](./PROJECT-DELIVERY-IMPLEMENTATION.md) 为准。现有本地候选使用方式见 [LOCAL-STABLE.md](./LOCAL-STABLE.md)。

## 交付目标

前端选定项目和发布版本后，能够安装对应组件包，在自己的工程里还原该版本的组件样式、状态和交互，并连接自己的业务数据。项目后续修改草稿或发布新版，不应自动改变已经接入的业务系统。

交付闭环：项目管理员保存规范 → 发布前检查 Runtime 归档 → 冻结规范数据 → 生成匹配版本的前端包 → 前端安装并接入 → 在版本页登记真实业务验收 → 显式升级或回退。

发布状态分为“规范数据快照”与“发布时可交付”。即使组件归档缺失，冻结规则数据仍可独立下载；但页面不得声称已有可执行组件包。

## 当前具备什么，还缺什么

|环节|当前事实|下一步|
|---|---|---|
|可执行组件|React / React Aria 控件已有独立 tarball、类型、CSS、字体和许可说明|声明支持的框架与浏览器范围，治理公共 API 和包体|
|项目配置|新增指定项目/发布版本打包，网页按权限读取冻结快照|保留原本地候选脚本作为独立验收，不将其默认配置当作项目交付|
|冻结版本|项目版本、完整快照 SHA-256 与匹配代码归档建立关联；缺失或损坏时拒绝生成|将运行时代码归档和已生成包纳入部署备份|
|独立取用|新增独立参考工程，验证 HTTP 校验、保存、错误恢复、持久化与包升级/回退|接入指定公司的真实业务工程|
|模式与模板|页面模板已提供 `page-template/1` 的槽位、数据、动作、状态、响应式和无障碍契约；交付包生成 `templates.json`|按真实业务需求继续增加已审批模板|
|分发|版本页按权限生成、下载 `@design-workspace/<项目>` 包|团队稳定使用后再接私有 npm 仓库|
|持续维护|已有版本差异、快照校验、运行时匹配和按业务系统登记的验收记录|补充兼容级别、弃用周期与团队通知机制|

当前源码入口：`scripts/package-local-delivery.ts`、`src/delivery/index.ts`、`consumer/`。本机候选的 `private: true` 与本地路径分发不能直接当作已完成的 npm 发布服务。

## 第一阶段交付形式

先做“一项目、一发布版本、一份可安装包”，沿用现有 tarball 能力，减少前端首次接入步骤。共享组件继续维护在同一套源码中，避免复制出多套独立维护的组件实现。

每份交付应同时包含：

|内容|前端用途|
|---|---|
|组件代码、样式与 TypeScript 声明|安装后直接使用正式控件，获得属性提示和类型检查|
|该项目该版本的变量、图标资源与主题入口|应用颜色、字号、密度、圆角及浮层样式|
|项目可用组件清单与适用状态|明确项目批准使用的组件和已验证能力|
|最小接入页与组合示例|演示表单、列表、弹窗如何连接调用方的数据与回调|
|接入说明和兼容矩阵|说明 React 版本、构建环境、CSS 引入、字体与浮层挂载要求|
|版本清单、变更说明、迁移说明|确认项目发布版本、组件代码版本、构建标识及升级影响|
|归档校验与第三方许可说明|验证收到的包完整并保留依赖来源|

项目发布版本与组件代码版本分别记录，不能只用一个文件名推断二者匹配。相同项目版本的已交付内容不可被后续构建覆盖。项目组件清单是使用约定，不是业务系统的权限控制。

等多个 React 项目稳定消费后，再考虑拆为“共享组件运行时 + 项目主题/配置包”，通过精确依赖或兼容范围关联。是否拆包应以真实接入和升级成本为依据。

## 前端的接入过程

1. **选择版本**：进入项目的版本记录，选择已发布版本，在“前端接入”区域查看支持环境、组件清单和变更说明。
2. **获取交付**：下载这一版本的组件包和接入说明；前端构建阶段持有获取权限，业务页面运行时无需登录设计管理平台。
3. **安装并锁定**：本地包先采用 `npm install ./收到的组件包.tgz --save-exact`，提交依赖锁文件；私有仓库启用后，由接入页生成真实包名和明确版本的安装命令。
4. **设置主题**：一次引入包内 CSS，并使用包内项目变量包裹应用或指定区域；通过正式 DS 浮层继承同一主题。多项目主题不得互相污染。
5. **连接业务**：业务工程传入字段值、表格数据、分页、校验结果和事件处理；API 请求、业务权限、路由与服务端校验由业务工程负责。
6. **验收页面**：从一个真实“查询列表 + 编辑表单”开始，核对组件状态、数据提交、错误恢复、键盘操作和窄屏表现。
7. **后续升级**：查看差异和迁移说明，显式安装目标版本、运行回归，再部署。回退时恢复上一份包和锁文件；涉及业务数据结构变更时另行制定数据回退方案。

当前包已经具备的最小组件用法如下，仅表示现有 React API；项目交付包的新用法见实现记录：

```tsx
import type { CSSProperties } from 'react'
import { DSButton, PreviewScope } from '@local/design-system'
import tokens from '@local/design-system/tokens.json'
import '@local/design-system/style.css'

export function ProjectAction({ saving, onSave }: {
  saving: boolean
  onSave: () => void
}) {
  return (
    <PreviewScope vars={tokens as CSSProperties}>
      <DSButton variant="primary" loading={saving} onClick={onSave}>
        保存
      </DSButton>
    </PreviewScope>
  )
}
```

正式接入文档应优先给出这种调用方控制数据和状态的示例。`TemplateExample`、`PatternExample` 的内置演示流程用于理解规范，其演示数据与模拟失败开关不应成为业务系统的数据层。

## 不同前端技术栈

- **React 项目**：优先直接安装正式组件，先在已验证的 React 19 环境接入。SSR、Next.js、其他 React 主版本等环境在验证后才进入支持矩阵。
- **Vue 或已有其他组件库的项目**：先交付设计变量、组件视觉/行为合同、状态用例和验收页面，由现有组件库做适配；当前 React 包不能直接当作 Vue 组件使用。
- **长期重复需求**：当多个同技术栈项目有稳定需求，再评估维护 Vue 实现或专门适配包。跨栈一致性验收以最终外观与行为为准。

## 顺序实施与验收

以下为原实施顺序；本轮已实现第 2–4 项并完成第 5 项的独立参考工程验收。第 1 项真实业务工程选择、第 5 项公司业务接入和第 6 项团队仓库配置仍需实际输入，不回写为上一轮 R01–R20 已实现的能力。

|顺序|工作|完成标准|
|---|---|---|
|1|确定首个接入业务工程与支持环境|记录技术栈、组件基础、构建方式和首个验收页面；明确是否直接安装 React 包|
|2|打包输入改为项目与发布版本|两个项目及同项目两个版本分别生成正确交付；草稿修改不影响旧包；缺代码关联时失败|
|3|形成正式消费入口与文档|安装、主题、类型、业务回调示例在干净工程通过；移除对管理站和示例数据层的运行依赖|
|4|增加版本页“前端接入”区域|查看者按项目权限获取说明和已生成包；项目管理员发起构建；有生成中、失败重试和就绪状态；下载不泄露其他项目数据|
|5|验证真实业务接入与发布回退|业务页面完成查询、编辑、提交和失败恢复；升级、回退各执行一次并保留记录|
|6|接入团队分发与持续维护|按团队需要选择私有 npm 仓库，约定发布角色、变更分级、弃用通知和维护责任|

构建与分发应使用服务端保存的完整版本数据，并保留对应的可执行源码/构建归档。安装包不能包含账号、会话或其他项目的专属资产。字体和兼容 Runtime 的包体问题列为正式消费验收项。

下一阶段的完成标准是：前端拿到交付物后，能在自己的业务工程中完成接入、升级和回退，并能定位到对应的项目规范版本。
