## 2. 下一个交付目标

建议先交付 **本地稳定版**，让设计师和开发者可以可靠完成以下流程：

1. 进入项目，配置主题并保存。
2. 查找项目实际可用的组件，查看真实状态和准确变量。
3. 在模式和模板中复用同一套组件，体验必要交互。
4. 查看指定冻结版本，所有页面保持同一版本上下文。
5. 按明确说明取用代码和对应资产，在独立示例中复现效果。

稳定版优先保证国科信 20 个核心组件，公共 88 项按成熟度展示。核心范围以外已经发现的 OTP、Avatar 等实际缺陷仍安排修复，不因未纳入 20 项而隐藏。

延续现有 React、React Aria、自研 Primitive、Runtime 和路由。平台外壳保持 App UI；项目示例使用项目主题。历史冻结包保持不可变。

## 3. 按依赖安排的制作批次

### 第 1 批：统一主题与版本的最终取值

**目的：先解决一个颜色在不同位置显示不同值的问题。**

- [ ] R01：统一组件预览、状态检查器、Token 详情的解析输出；保留明确的值、来源、项目和版本。
- [ ] R02：所有 Portal 传递完整语义与组件变量，消除项目弹窗蓝底绿边等混用。
- [ ] R03：冻结主题、Token 详情、模式和模板读取同一冻结上下文；缺失数据明确说明，不静默使用草稿。
- [ ] R04：修复占位色可读性，加入品牌文字/背景对比度检查；品牌值调整需有设计依据。
- [ ] R05：明确字体、字号、间距、尺寸到各组件配方的映射，界面说明与实际联动一致。

对应审计：F01–F04、F07，以及 F03 中 Pattern 版本读取问题。

交付物：统一解析接口、消费点修复、对比测试与浏览器证据。

**验收出口：** 同一个项目/版本/状态，在详情、预览、弹窗和取用资产中一致；公共层不被项目污染；切换回历史版本不混入草稿。允许历史品牌不同，禁止篡改历史包。

### 第 2 批：修复真实缺陷，补齐核心组件状态

**目的：让组件在异常、重复操作和组合条件下可靠。**

- [ ] R06：修复 invalid+hover/focus 优先级，补齐复合字段错误/禁用、日期焦点和选择控件组合态。
- [ ] R07：修复 OTP 非顺序输入、Toast 关闭重开计时、Avatar 失败后换图恢复。
- [ ] R08：修复 Tag 移除示例、Loading 尺寸、Select 清空图标与窄屏 Drawer。
- [ ] R09：整理 88 项状态适用性：已实现、待实现、不适用；删除虚假状态声明和重复示例。
- [ ] R10：对核心 20 项建立 API—状态—示例—测试证据对应关系；将关键场景同步到 Storybook。

对应审计：F05、F08–F10，S01–S08；与第 1 批重叠的映射问题不重复计数。

建议组件顺序：Button / Input / Select → Checkbox / Radio / Switch / Form / Field → Table / Pagination → Dialog / Drawer / Toast → Upload / Feedback。OTP/Avatar 可作为独立缺陷插入本批。

交付物：组件修复、适用状态矩阵、真正验证操作后结果的回归测试。

**验收出口：** 核心组件的必需状态与组合态逐项有证据；公开的次级组件缺陷不再阻断基础使用；点击、键盘、长内容和窄屏表现符合约定。491 项测试仅作为基线，不作为唯一放行条件。

### 第 3 批：完成模式与模板的真实复用

**依赖：第 1、2 批中所需组件先通过验收。**

- [ ] R11：12 个 Pattern 的示例统一使用正式 DS 控件；区分说明步骤与可执行业务示例。
- [ ] R12：查询列表、详情、表单三类模板补齐适用的空数据、无结果、加载、错误、校验、长内容和只读情况。
- [ ] R13：优先做通“筛选 → 列表 → 详情/编辑 → 反馈 → 返回”的一条代表流程，再复用到其他模式。
- [ ] R14：统一命名、操作位置、清空/关闭/移除语义及返回行为；修复指向当前项目不可用组件的关联入口。
- [ ] R15：预览与复制的使用代码采用相同组件、参数、主题和版本；验证依赖说明。

交付物：可复用的模式组合、三类可靠模板、示例代码和场景验收记录。

**验收出口：** 模式与模板中的同一组件保持同样状态表现；组合页面不再维护另一套业务控件样式；使用者可按说明复现关键场景。

### 第 4 批：补齐本地版本交付与使用闭环

**目的：从“本机能看”到“指定版本能够可靠取用”。**

- [ ] R16：检查新本地冻结快照包含的真实内容；明确 tokens、components、icons、recipes、patterns 等哪些是本版快照、哪些是兼容引用。
- [ ] R17：增加明确的备份/恢复或导出/导入方式及格式校验，覆盖项目和版本关联；先定义最小交付格式再实现。
- [ ] R18：版本对比从索引差异逐步扩展到实际 Token/组件/资产差异；尚未提供的差异不推测。
- [ ] R19：用独立 Consumer 示例验证指定版本的组件、样式和资源，避免只在管理站内部自证正确。
- [ ] R20：补齐快速开始、组件成熟度、已知限制和版本说明，更新旧文档中已不成立的准入结论。

交付物：本地稳定版候选、版本化交付包/备份、消费侧样例和使用说明。

**验收出口：** 新快照来源明确、可重现、历史不被改变；按文档在独立样例中成功使用；核心流程没有未关闭的 P1 问题。此时再决定正式版本号，不预先把候选叫作“已发布”。

### 第 5 批：设计资产交付（候选扩展）

在组件契约稳定后，按需安排：

- 核心 20 个组件 Storybook 收尾与使用指南。
- Figma 变量、基础样式、组件 Variant 和状态，与同一 Token/组件清单对照。
- Code Connect 映射及版本对应关系。
- 先验证一个完整组件族，再扩展到全部核心项；不把重复别名当成新增成熟组件。

此批不在本次规划中自动执行 Figma 写入。是否优先于多人协作，应由实际使用目标决定。

### 第 6 批：团队化与智能能力（另立需求）

根据后续使用需要选择，不默认全部建设：

| 使用需要 | 制作方向 | 开始前的条件 |
| --- | --- | --- |
| 多人共用、跨设备保存 | 服务端存储、真实鉴权、项目角色、操作记录、并发冲突处理 | 明确部署方式、协作对象、数据模型 |
| 规范自动检查 | 先做确定性 Token/状态/引用校验，再接真实页面或设计输入 | 规则有可验证的期望结果与错误证据 |
| AI 辅助生成/检查 | 在稳定组件契约、模式和版本之上生成或解释 | 真实调用链、失败反馈、人工复核与质量评价 |
| 更复杂的搭建需求 | 再评估可视化布局编辑、更多业务模板或平台 | 有具体任务证明当前模板/组合无法满足 |

这些内容在当前 PRODUCT.md 中属于未实现或不在当前范围的能力；这里只记录候选方向，不能当作已确定开发承诺。

## 4. 当前建议先执行的任务包

第一包锁定 R01–R04：**取值统一 → Portal 继承 → 冻结隔离 → 对比度修复**。

原因：这四项影响全站，多做组件页面会放大偏差。第一包验收后再扩展状态和模板，可减少重复返工。

下一包 R06–R09 处理已经复现的交互和状态缺陷；R05 的具体文字配方映射可以与其共同验收。外部服务、全新页面类型与视觉重做不挤占这两包。

## 5. 进度管理方式

统一使用以下状态：**待开始 → 制作中 → 待验证 → 已验收**；“阻塞”注明依赖。仅写完代码或测试能挂载，都不能标记已验收。

每个任务至少记录：任务 ID、对应问题、受影响范围、实现提交/文件、自动检查、浏览器验证、遗留限制。验证覆盖以下层次：

| 层次 | 需要回答的问题 |
| --- | --- |
| 定义 | 该状态是否适用？变量和 API 语义是否唯一？ |
| 实现 | 默认、交互、异常和恢复路径是否真的工作？ |
| 组合 | 项目/版本/主题/浮层/页面组合是否一致？ |
| 使用 | 复制代码或消费指定版本后能否复现？ |

每批完成后更新一次本文进度与审计项状态，保留原始问题证据。问题合并时标记重复来源，不把 F/S 数量简单累加，也不删掉尚未验证的问题。

工期目前缺少投入人数、可用时间和发布节点，不给出伪精确日期。以上是执行顺序与验收批次；第 1 批完成后，可依据实际工作量滚动排期。
